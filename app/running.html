Tobyn's Schedule Reader

Note: This is built for humanities classes.

Running it yourself

The website does everything most people need, and it needs nothing installed. This page is for when you want the whole thing on your own machine: a folder of readings rather than one syllabus at a time, search across all of it, and your own published copy.

It's all local. No keys, no account, no server of mine anywhere in it.

What you'll need

Python 3.11 or newer, and git. That's the lot.

Getting it set up

git clone https://github.com/tobyn-smith/reader
cd reader
python -m venv .venv
.venv/Scripts/activate
pip install -e ".[dev]"

On macOS or Linux the fourth line is source .venv/bin/activate instead. If you're going to send changes back, add git config core.hooksPath .githooks so the pre-commit hook can stop your coursework wandering into a commit.

The commands you'll actually use

CommandWhat it does
vault syllabus syllabus.pdf Reads a syllabus, shows you what it found, saves it once you're happy.
vault ingest readings/ Adds a folder of reading PDFs and matches them to the schedule. Safe to run again.
vault status This week: what you've got, what's missing, what's due.
vault search "commitment problem" Full text, across every reading you've taken in.
vault build --public --pdf Builds the site, exactly as GitHub Pages serves it.
vault serve Opens the private build, the one with everything in it.

Where your things live

Your database, PDFs and caches sit in ~/.seminar-vault/, well outside the repository, so nothing you're reading for a class can end up in a commit by accident.

Optional extras

One feature each, and everything else carries on working without them.

Publishing your own copy

  1. Fork it, then Settings, Pages, and set the source to GitHub Actions.
  2. Run vault syllabus your-syllabus.pdf for each course and check the parse before saving it.
  3. Run vault ingest your-readings/ as the term goes on.
  4. Run vault export --public, read what it kept and what it dropped, then commit data/public.json. Pushing publishes.

Nothing reaches the public site unless it's named on an allowlist, and the tests fail if something new turns up in there. Schedules, citations, deadlines and bibliographies are allowed out. Reading text, notes and your instructor's contact details stay on your machine. The allowlist, the CI setup and the hook all carry over to your fork.

Running the tests

pytest -q

Offline, no keys. The fixtures are invented syllabi copying the layouts real ones use: bulleted schedules with odd glyph markers, ruled tables with two meetings a week, labelled topic blocks, two-column articles, and one scan with no text layer at all. They assert exact reading counts per week, because a parser quietly losing one reading in five otherwise looks perfectly healthy.

One thing worth knowing

The command line and the website run the same Python, compiled to WebAssembly for the browser. They don't get quite the same information out of a PDF, though: on your machine it can see the ruled lines a table is drawn with, and in the browser it can't, so a handful of files come out slightly better on the command line. The accuracy figures on the front page are the browser's, since that's what most people are using.

ARCHITECTURE.md in the repository has the rest of it, including what the parser gets wrong and why.
